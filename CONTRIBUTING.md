# Contributing to CCPM-Registry

Thanks for helping grow the registry!
This repository lists the packages [CCPM](https://github.com/SorcerioTheWizard/ComputerCraft-Package-Manager) can install, and holds the Python tools that check, build, and sync it.
Changes to the `ccpm` client itself belong in its own repository.

## Ways to Contribute

- **Publish a package** or a new version of one, as described below.
- **Fix a synced package** from Pinestore or another external source with an override.
- **Report a problem** with a package or the registry by opening an issue.
- **Improve the tools** that validate, build, and sync the registry.

## Publishing a Package

The [README](README.md#publishing-a-package) explains the package format in full. In short:

1. Host your files at raw URLs on an [allowed host](README.md#allowed-hosts), pinned to the exact content you are publishing.
2. Add `packages/<name>/package.json` if the package is new.
3. Add `packages/<name>/<version>.json`. If your files are in a public GitHub repository, one command writes it with every file pinned and hashed:

    ```bash
    uv run ccpm-registry manifest <name> <version> <repo path>=<install path> ... --github <owner>/<repo> --ref <tag or commit>
    ```

    Otherwise, hash each file with `uv run ccpm-registry hash <url>` and write the manifest by hand.
4. Run `uv run ccpm-registry validate` and fix anything it reports.
5. Open a pull request. CI validates the registry and downloads your new files to confirm their hashes.

Published versions never change. To fix a release, publish a new version.

## Fixing a Synced Package

Packages under `external/` are generated by `ccpm-registry sync`, and any hand edit is overwritten by the next daily sync.
To correct one, add an entry to `external/<source>/overrides.json`, keyed by the project's ID in the source, which is the `id` in its package's `origin`:

```json
{
    "$schema": "../../schemas/overrides.schema.json",
    "123": {
        "note": "The listed command downloads the installer instead of running it.",
        "command": "wget run https://example.com/install.lua"
    }
}
```

Overrides can replace the install command, install a file as a library, add dependencies and compatibility ranges, choose the name of a new package, or skip a project entirely.
`schemas/overrides.schema.json` describes every key.
If you are the project's author, fixing the project on its source is even better, since the sync picks up the change the next day.

## Working on the Tools

The tools are Python, managed by [uv](https://docs.astral.sh/uv/):

```bash
uv sync                             # Install the tools
uv run pytest                       # Test the tools
uv run ccpm-registry validate       # Check the registry offline
uv run ccpm-registry verify         # Download every published file and check its hash
uv run ccpm-registry build          # Write the published form to `dist/`
uv run ccpm-registry sync <source>  # Mirror an external source into `external/<source>/`
```

- Always run Python through `uv run`, never with a bare `python` or `pip`.
- Add and remove dependencies with `uv add` and `uv remove`, never by editing `pyproject.toml` by hand.
- Tests never touch the network. Use `httpx.MockTransport` and the `builder` fixture in `tests/conftest.py`.
- The version range rules in `semver.py` are shared with the client's `semver.lua`; change both together.
- `build.py` writes the format clients read. Bump `INDEX_FORMAT` for any change clients cannot safely ignore.

## Adding an External Source

Each external catalog has one adapter in `src/ccpm_registry/sources/`.
An adapter only turns the catalog into `ExternalProject`s; `sync.py` handles naming, versioning, overrides, and delisting for every source.

1. Add `src/ccpm_registry/sources/<source>.py` with a class that has a `name` and a `fetch(client)` method, following `pinestore.py`.
2. Register it in `SOURCES` in `src/ccpm_registry/sources/__init__.py`.
3. Add tests with a mocked catalog response, then add a step for it to `.github/workflows/sync.yml`.
4. If installs should be reported back to the source, add a reporter for it to the client's `src/lib/ccpm/origins.lua`.

## Code Style

The full rules are in [CLAUDE.md](CLAUDE.md). In short:

- Every module starts with a docstring: a title, a blank line, and a one line description, and is split into `# MARK: Imports`, `# MARK: Constants`, `# MARK: Functions`, and similar sections.
- Functions have Google Style docstrings, with backticks around code references.
- Nearly every logical block gets a short imperative comment, like `# Check the hash`.
- Use American English, never use em dashes, and keep each sentence of prose on one line.

## Pull Requests

1. Branch from `master`.
2. Make your change, with tests for tool changes.
3. Run `uv run pytest` and `uv run ccpm-registry validate`.
4. Open a pull request; the default template covers packages, features, and general changes.
   For a bug fix, use the bug template by adding `?template=bug.md` to the pull request URL, like `https://github.com/SorcerioTheWizard/CCPM-Registry/compare/master...<your branch>?template=bug.md`.
5. CI tests the tools, validates the registry, and checks the hashes of new files; it must pass before merging.

Commit messages are a short imperative subject line with no body, like `Add orescanner`.
